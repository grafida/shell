# Troubleshooting

## Logs

The shell writes its own log and your worker's **standard error** to one file, `shell.log`, rotated to `shell.log.1` …
`shell.log.3` (the oldest is dropped). Everything your PHP code writes to stderr (`error_log()`, `fwrite(STDERR, …)`,
PHP warnings and notices, and anything echoed by a handler, tagged `[stray-output]`) ends up there.

`logDir` in the [manifest](manifest.md) is `"auto"` by default, which means (with `<dataDir>` being the manifest's
`dataDir`, or its `id`):

| Platform | Directory |
|---|---|
| Linux | `$XDG_STATE_HOME/<dataDir>/logs` (default `~/.local/state/<dataDir>/logs`) |
| macOS | `~/Library/Logs/<dataDir>` |
| Windows | `%LOCALAPPDATA%\<dataDir>\Logs` |

Set `logDir` to an absolute path to put it elsewhere. Tell your users where it is; it is the first thing you will want
in a bug report.

## Tags in worker output

| Tag | Origin |
|---|---|
| `[stray-output]` | Something a handler printed to stdout. It is diverted to stderr so it cannot corrupt the protocol. Remove the `echo`/`var_dump`. |
| `[handler-error]` | An exception escaped your handler; the page got `500 internal_error`. The full exception follows. |
| `[response-error]` | Your response was too large (`response_too_large`) or invalid (`bad_response`). |
| `[protocol-error]` | The shell and the worker disagree about the protocol. This is a bug in one of them; report it. |

## Alerts at start-up and while running

The shell shows a native alert when it cannot continue. The message is also in the log.

| What the user sees | Cause | Fix |
|---|---|---|
| The manifest is invalid, naming a member | `shell.json` fails the [schema](manifest.md), for instance a typo | Fix the named member |
| "No shell.json found", listing the places it looked | The manifest is not beside the shell (or in `../Resources`) | Check the package layout |
| "The worker … is missing. It should be beside the shell" | `worker.binary` names a file that is not there | Make `worker.binary` match the packaged stub's name, and check the package |
| The worker never became ready, or exited before `ready` | Your start-up code threw, printed to stdout, or took longer than `worker.readyTimeoutMs`; or a PHP extension missing from the packaged runtime made the bootstrap fail | Read the end of stderr in the alert (the last 40 lines), then the log. Run `bin/worker.php` through `WorkerProcess` in a test. |
| The worker keeps crashing | More than `worker.restart.max` crashes in `restart.windowSeconds` | The alert shows the last 40 lines of stderr. Look for a fatal error, a segfault or an out-of-memory kill. |
| WebView2 is missing (Windows) | The Evergreen runtime is not installed | [Install it](packaging.md#windows-requirements) |
| The app does not start at all on Linux; the launcher shows packages to install | The system lacks WebKitGTK 4.1 or GTK 3, or has too old a glibc | See the [system requirements](packaging.md#linux-requirements) |

A worker that cannot start once is not retried; a failure **before its first `ready`** is always fatal.

A crash *after* `ready` is survived: the in-flight request gets `502 {"error":"worker_restarted"}`, a new worker starts,
and your page should retry or show an error. State kept only in the old worker's memory is lost.

To keep the alerts on the terminal (in tests or headless runs), set `SHELL_ALERTS=stderr`.

## Errors that your page sees from the shell

These are generated by the shell without involving your PHP code:

| Status and body | Meaning |
|---|---|
| `403 {"error":"cross_origin"}` | The request carried an `Origin` other than your app's, for example from an embedded `<iframe>`. |
| `404 {"error":"bad_path"}` | The URL's path contains an escaped slash or NUL (`%2F`, `%00`), which Apache also refuses by default. Put such values in the query string instead. |
| `413 {"error":"body_too_large"}` | The request body exceeds `worker.maxBodyBytes`. |
| `502 {"error":"worker_restarted"}` | The worker died while handling this request. |
| `400 {"error":"unknown_file_token"}` / `stale_file_token` | An `X-Shell-File` token is not one the shell issued this session. |
| `404`, `405`, `409 dialog_busy`, … | Native-endpoint errors, see [the JavaScript side](javascript.md#handling-errors). |

These come from the worker library:

| Status and body | Meaning |
|---|---|
| `500 {"error":"internal_error"}` | An exception escaped your handler. See `[handler-error]` in the log. |
| `500 {"error":"response_too_large"}` | Your response body exceeds the limit. |
| `500 {"error":"bad_response"}` | Your response could not be encoded. |

## Common problems

**macOS says the app is "damaged" or from an unidentified developer; Windows says "Windows protected your PC".**
The build is unsigned (or, on macOS, signed only ad hoc). Sign it, or see the [caveats of unsigned
builds](packaging.md#unsigned-builds) for how users can open it anyway.

**It works with `--dev` but not once packaged.**
Almost always one of: a file that no `phar.include` rule matches; an extension that the
[packaged runtime](packaging.md#the-php-runtime-inside-the-package) does not have; or code writing next to itself or
relying on the working directory (the PHAR is read-only, and the working directory differs; use `__DIR__` and a per-user data directory). Run the packaged build with the log open.

**My `echo` or `var_dump` does nothing.**
Handlers' output is diverted to the log by design. Read `shell.log`, or use `error_log()`.

**The app is slow when I do something heavy.**
The worker handles one request at a time. A long request blocks all others. Shorten it, or push the work to a child
process and let the page poll.

**My changes to PHP are ignored.**
The worker is long-lived and loads code once. Restart the shell. If you see old code in a *packaged* app, you are
running a stale build.

**localStorage / IndexedDB data vanished after an update.**
Page storage is keyed to the origin `<scheme>://app` and kept in the webview's data directory (`dataDir`). Changing
`scheme`, `id` or `dataDir` between releases abandons it.

**The window is blank on Linux with an NVIDIA GPU.**
That is what `webview.dmabufRenderer` is for. `"auto"` turns the renderer off when NVIDIA's driver is detected; set it
to `"off"` to force that, or set `WEBKIT_DISABLE_DMABUF_RENDERER=1` in the environment (the user's variable always wins).

**A shortcut I handle in JavaScript does not reach the page.**
Menu accelerators fire before the webview. Add the chord to `menu.reservedChords`, or set `menu.preset` to `"none"`.

**A link opens in the browser instead of in my window.**
By design: an off-origin `http(s)` link the user activates is handed to the system browser, and other schemes are
refused. See [Links and navigation](javascript.md#links-and-navigation).

**Spell check does nothing on Linux.**
The system has no Hunspell dictionary for the user's language.

## Inspecting the page

Set `webview.devtools` to `true`, or to `"env:MYAPP_DEBUG"` and start the app with that variable set. The webview's web inspector is then enabled; how you open it
depends on the platform's webview (typically the right-click menu, which needs `webview.contextMenu`).

## Reporting bugs in the shell

Include: the shell version (`grafida-shell --version`; or `await GrafidaShell.info()` from the page), the operating system
and webview version (`info()` reports it), the manifest, and the relevant part of `shell.log`. Issues go to
[grafida/shell](https://github.com/grafida/shell/issues), [grafida/shell-php](https://github.com/grafida/shell-php/issues)
or [grafida/shell-packager](https://github.com/grafida/shell-packager/issues), depending on which piece misbehaves.
