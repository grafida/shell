# Shell ↔ worker wire protocol, version 1

- **Status:** v1, frozen. A wire-incompatible change is a new version; see "Versioning".
- **Implementations:** `src/protocol.rs` in this repository (the shell side) and
  `Grafida\Shell\Frame\*` in [grafida/shell-php](https://github.com/grafida/shell-php) (the worker
  side). Both run every conformance fixture in [`fixtures/`](fixtures/).
- **Context:** grafida/grafida#82 (design), grafida/grafida#84 (this specification).

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Transport

The shell spawns the worker with piped stdio and talks to it over two byte streams:

| Stream | Direction | Carries |
|---|---|---|
| worker **stdin** | shell → worker | frames |
| worker **stdout** | worker → shell | frames, and nothing else |
| worker **stderr** | worker → shell | free-form UTF-8 log text; never parsed as frames |

Both frame streams are a plain concatenation of frames. There is no other framing, no
compression and no padding. A stream ends with **EOF at a frame boundary**. EOF anywhere else is a
protocol error (`truncated`).

## 2. Frame layout

```
offset   size  field
0        4     magic: the ASCII bytes "GSF1" (0x47 0x53 0x46 0x31)
4        4     H: header length in bytes, unsigned 32-bit little-endian
8        H     header: a JSON object, UTF-8 (RFC 8259)
8+H      8     B: body length in bytes, unsigned 64-bit little-endian
16+H     B     body: raw bytes, never base64 or otherwise transformed
```

Limits. A receiver MUST enforce both, and MUST do so **before** reading the bytes the length
announces:

| Limit | Value | Error when exceeded |
|---|---|---|
| `H` | at most **1 MiB** (1 048 576), fixed | `header_too_large` |
| `B` | at most **128 MiB** (134 217 728) by default; the shell's manifest may change it (`worker.maxBodyBytes`), and the worker MUST be given the same value | `body_too_large` |

The two limits exist so that a corrupt or hostile length can never make a receiver allocate memory
or wait for bytes that will not come. In particular, `B = 2^64 − 1` is a `body_too_large` error,
**not** a wait for 16 EiB.

## 3. Header

The header is a JSON object with a string member `type`. There are four types: `ready`, `request`,
`response` and `shutdown`. Members are defined per type below. A receiver:

- MUST ignore members it does not know, so a later v1 revision can add optional members;
- MUST reject a member it knows whose value has the wrong JSON type or is out of range;
- MUST treat absent optional members as absent, never as an empty value it invents;
- MUST NOT rely on member order.

A sender MUST NOT emit duplicate member names at any level, and receivers need not detect them. The
header SHOULD NOT carry a byte-order mark. Strings MAY be written with raw UTF-8 or with `\u`
escapes (surrogate pairs included); the two are equivalent.

**Integers.** Every integer member is a JSON number without a fraction or exponent: `17`, not
`17.0`, `1.7e1` or `"17"`. Every integer is in **0 … 2^53 − 1** (9 007 199 254 740 991) unless
its row below narrows it further. Ids are therefore u64 values that every JSON implementation,
JavaScript's included, reads exactly, and that both a Rust `u64` and a PHP `int` hold without
loss. A receiver rejects an integer outside its range; it never clamps or wraps it.

### 3.1 `ready` (worker → shell, exactly once, first)

```json
{"type": "ready", "protocol": 1, "pid": 4242, "app": "grafida", "version": "1.4.0"}
```

| Member | Required | Value |
|---|---|---|
| `protocol` | yes | integer ≥ 1: the protocol version the worker speaks |
| `pid` | yes | integer ≥ 0: the worker's process id |
| `app` | no | string: the application's name, for logs |
| `version` | no | string: the application's version, for logs |

The body MUST be empty (`B = 0`).

### 3.2 `request` (shell → worker)

```json
{"type": "request", "id": 17, "method": "POST", "url": "boson://app/api/drafts/3",
 "headers": {"content-type": ["application/json"]}}
```

| Member | Required | Value |
|---|---|---|
| `id` | yes | integer, 0 … 2^53 − 1 |
| `method` | yes | string: a non-empty HTTP token (RFC 9110 `tchar`s). Case is preserved, not normalised. |
| `url` | yes | non-empty string: the absolute URL the webview asked for, **verbatim** |
| `headers` | yes | a header map (§3.5) |

The body is the request body, which may be empty.

The URL is passed through exactly as the webview reported it. A receiver MUST NOT decode,
re-encode or normalise it in the codec: percent-escapes stay escaped and raw non-ASCII stays raw.
Interpreting it (path, query) is the application's business.

### 3.3 `response` (worker → shell)

```json
{"type": "response", "id": 17, "status": 200,
 "headers": {"content-type": ["application/json"], "cache-control": ["no-store"]}}
```

| Member | Required | Value |
|---|---|---|
| `id` | yes | integer, 0 … 2^53 − 1: the `id` of the request being answered |
| `status` | yes | integer, 100 … 599 |
| `headers` | yes | a header map (§3.5) |

The body is the response body, which may be empty. The shell does not add a `content-length`; the
body's length is `B`.

### 3.4 `shutdown` (either direction, optional)

```json
{"type": "shutdown"}
```

Shell → worker: finish the request in progress, if any, then exit 0. Worker → shell: the worker is
about to exit on its own (it is not a crash). The body MUST be empty.

### 3.5 Header maps

A JSON object mapping each header **name** to a **non-empty array of string values**:

```json
{"accept": ["text/html", "application/json"], "x-multi": ["one", "two"]}
```

- Names are **lower-case** HTTP tokens: one or more of ``a-z 0-9 ! # $ % & ' * + - . ^ _ ` | ~``.
  A receiver MUST reject an upper-case name rather than fold it. Senders lower-case.
- Values are arrays, so a header that appears more than once keeps **every** occurrence, in order.
  This is a hard requirement: collapsing repeated headers was one of the reasons Phase 0 rejected a
  stack (ADR 0001). A sender MUST put all occurrences of one name into one array.
- A value MUST NOT contain CR (U+000D), LF (U+000A) or NUL (U+0000). These would let one header
  smuggle another into the webview's HTTP layer.
- An empty array is an error; an absent header is expressed by leaving the name out.
- The empty object `{}` is a valid map. A JSON array, even an empty one, is not.

## 4. Receiving: the order of checks

Both implementations MUST check in this order and report the **first** failure. The order is
normative so that a given byte sequence produces the same error code everywhere, and the fixtures
depend on it.

1. **Magic.** Read up to 4 bytes. EOF before the first byte is the clean end of the stream. EOF
   after 1–3 bytes → `truncated`. Bytes other than `GSF1` → `bad_magic`. A receiver MUST NOT scan
   ahead for the next magic: a stream that has lost sync is not recoverable, and stopping at once is
   what turns stray output into an error instead of a hang.
2. **H.** Fewer than 4 bytes → `truncated`. `H` > 1 MiB → `header_too_large`.
3. **Header bytes.** Fewer than `H` bytes → `truncated`.
4. **JSON.** Not valid UTF-8 JSON (an empty header included) → `bad_json`.
5. **Header shape**, in this order:
   1. not a JSON object, or `type` missing or not a string → `bad_header`;
   2. `type` not one of the four → `unknown_type`;
   3. any member of that type missing or invalid (§3) → `bad_header`.
6. **B.** Fewer than 8 bytes → `truncated`. Then, in this order:
   1. a non-zero `B` on `ready` or `shutdown` → `bad_header`;
   2. `B` above the receiver's body limit → `body_too_large`.
7. **Body.** Fewer than `B` bytes → `truncated`.

Because the header is checked (step 5) before `B` is read (step 6), a malformed header is reported
as soon as it has arrived, without waiting for a body.

### Error codes

| Code | Meaning |
|---|---|
| `truncated` | EOF inside a frame |
| `bad_magic` | the frame does not start with `GSF1` |
| `header_too_large` | `H` exceeds 1 MiB |
| `body_too_large` | `B` exceeds the body limit |
| `bad_json` | the header is not valid UTF-8 JSON |
| `bad_header` | the header is valid JSON but breaks §3, or a body is present where none is allowed |
| `unknown_type` | `type` is a string naming no v1 frame type |

These codes are the vocabulary the fixtures, the tests and the logs share. Implementations MAY
attach a human-readable message, but tests compare the code only.

**Every protocol error is fatal to the stream.** Once a frame is malformed the stream is out of
sync, so the receiver stops reading. A worker logs the error to stderr and exits with status 65
(§6). The shell treats it as a worker crash.

## 5. Session

```
worker                                shell
  │ ── ready ──────────────────────────▶ │   first frame on stdout; nothing precedes it
  │ ◀────────────────────────── request │   id 1
  │ ── response ───────────────────────▶ │   id 1
  │ ◀────────────────────────── request │   id 2
  │ ── response ───────────────────────▶ │   id 2
  │ ◀──────────────────────── shutdown  │   (optional) or EOF on stdin
  │ exits 0
```

- The worker writes `ready` before it reads anything, and nothing before `ready`. The shell sends
  no request until it has received `ready`, and refuses a `ready` whose `protocol` differs from its
  own version (it reports a version mismatch rather than talking past the worker).
- The shell assigns ids, monotonically increasing. The worker answers each request with exactly
  one `response` carrying the same id.
- **v1 has one request in flight at a time.** The shell sends request *n + 1* only after the
  response to *n* has arrived. Ids already make pipelining or a worker pool a non-breaking change
  later.
- A frame of a type the receiver's role does not accept (a `request` sent to the shell, a `ready`
  or `response` sent to the worker, a second `ready`, a `response` whose id was not asked) is a
  session error. The codec decodes such a frame normally. The session layer then treats it like a
  protocol error.
- **EOF on the worker's stdin** at a frame boundary means "exit now": the worker exits 0 without
  answering anything further. The shell closes stdin to shut the worker down. The `shutdown` frame
  is a courtesy that lets the shell distinguish "please exit" from "the shell died".

## 6. Worker obligations (normative for every worker implementation)

- **stdout carries frames only.** A worker MUST keep anything else off stdout: PHP warnings, stray
  `echo`, a library's debug print. The reference worker in shell-php sets `display_errors=stderr`,
  writes frames through a dedicated stdout handle with an explicit flush after every frame, and
  captures every handler call's output buffer, which it sends to stderr tagged `[stray-output]`.
- **A handler failure is a response, not a crash.** If the application throws, the worker answers
  `500` and keeps serving.
- **Exit status:** `0` after EOF or `shutdown`; `65` (`EX_DATAERR`) after a protocol or session
  error; `74` (`EX_IOERR`) when stdout cannot be written, e.g. because the shell has gone. The shell
  logs the status; any non-zero status is a crash for its restart policy.

## 7. Versioning

The protocol version is the integer in `ready.protocol`. It changes only for a wire-incompatible
change: the frame layout, the meaning of an existing member, a new required member, or a new frame
type that a v1 peer would have to understand. Adding an optional member is not a version change,
because receivers ignore unknown members (§3).

`PROTOCOL_VERSION` in this crate and `Grafida\Shell\Protocol::VERSION` in shell-php MUST be equal.
The magic `GSF1` does not change with the protocol version: version negotiation is the handshake's
job, not the magic's.

## 8. Conformance fixtures

[`fixtures/`](fixtures/) holds pairs of files with the same base name:

- `NAME.bin`: a byte stream, i.e. zero or more frames, possibly ending in a malformed one;
- `NAME.json`: what a receiver must make of it, using the default limits (1 MiB header,
  128 MiB body).

```jsonc
{
  "description": "One sentence: what this case pins down.",
  "frames": [                         // every frame decoded before the stream ends, in order
    {
      "header": {"type": "request", "id": 1, "method": "GET", "url": "…", "headers": {}},
      "body": {"length": 0, "sha256": "e3b0…", "text": ""}
    }
  ],
  "end": "eof"                        // "eof" for a clean end, otherwise an error code from §4
}
```

- `header` is the decoded header in **normal form**: only the members §3 defines for that type,
  with optional members present only if they were sent. Unknown members are left out.
- `body.length` and `body.sha256` (lower-case hex) are always present. `body.text` (UTF-8) or
  `body.base64` is added when the body is small enough to read in the file. Where one is present, it
  must match too.
- `SHA256SUMS` (in `sha256sum` format) lists every fixture file. Both test suites check it, so an
  edited fixture is caught, and the copy shell-php vendors can be compared with the one here.

What the test suites do with them:

1. **Decode.** Decode `NAME.bin` with the default limits. The frames and the `end` must match
   `NAME.json` exactly. A receiver must reach `end` from the bytes alone. It must never wait for
   input beyond the file, so a fixture can never hang a correct implementation.
2. **Round trip.** Encode each expected frame, decode the result, and check that the same frame
   comes back. (Byte equality with `NAME.bin` is **not** required, because JSON serialisers differ
   in escaping and member order. The fixtures pin down meaning, not one serialiser's output.)

**A failing fixture is a question about which side is wrong, never a file to regenerate.** The
`.bin` files were produced by a third, independent writer, `scripts/protocol/make-fixtures.py`,
and are not output of either codec under test. That script only adds fixtures that do not exist
yet and refuses to overwrite one. Changing an existing fixture is a change to the protocol: it
needs a reason in the commit message, and it bumps the version if it is wire-incompatible.
